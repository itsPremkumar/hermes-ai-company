# verify-ai-claims — verify pasted AI output before trusting it

## When to use
The user pastes text that is clearly generated by *another* AI (reads like a
polished report: 'As of July 2026...', citation footnotes [1][2], two-tool
comparison tables, 'recent industry coverage'). **This is a STANDING RULE,
not a one-off:** confirmed via clarify on 2026-07-14 — the user's default for
pasted AI output is **VERIFY it (check claims/commands are real & correct, run
or fetch what's verifiable, explicitly flag any fake/wrong parts), THEN improve
or act on it. Do NOT accept at face value.** This is distinct from the user's
own words (third-person report tone + citations = the signal). The two-step
default is non-negotiable: a verdict alone is not enough — deliver the corrected,
working result.

## Procedure (the proven method)
1. **Classify claims.** Separate (a) factual/quantitative assertions (stars,
   license, dates, versions, specs, prices) from (b) opinion/positioning
   (usually fine).
2. **Re-pull live primary sources for every number — and VERSION/DATE too.**
   AI comparison docs hallucinate THREE measurable things, not just stars:
   (a) star/fork counts, (b) **version numbers**, (c) **release/launch dates**.
   For versions/dates pull the release endpoint, not just the repo root:
   ```bash
   # latest published release: tag + date
   timeout 20 curl -s 'https://api.github.com/repos/<owner>/<repo>/releases/latest' | python -c 'import sys,json;d=json.load(sys.stdin);print(d.get("tag_name"),d.get("published_at"))'
   # recent tags (confirm a claimed version string actually exists)
   timeout 20 curl -s 'https://api.github.com/repos/<owner>/<repo>/tags?per_page=5' | python -c 'import sys,json;print([t.get("name") for t in json.load(sys.stdin)[:5]])'
   ```
   - **Guard the GitHub API.** Rapid successive `api.github.com` pulls can hit
     rate limits or return a JSON error object — pipe through `python -c
     'json.load(...)'` and on `KeyError`/`TypeError` retry once with a 2s sleep.
     Don't treat a rate-limit blob as real data.
   - GitHub stats:
     ```bash
     timeout 20 curl -s 'https://api.github.com/repos/<owner>/<repo>' | python -c 'import sys,json;d=json.load(sys.stdin);print(d.get("stargazers_count"),d.get("license",{}).get("spdx_id"),d.get("open_issues_count"),d.get("created_at"))'
     ```
     Canonical repos: `OpenClaw/OpenClaw`, `NousResearch/hermes-agent`,
     `paperclipai/paperclip`.
   - Narrative/claim cross-checks:
     `curl -s 'https://r.jina.ai/https://html.duckduckgo.com/html/?q=<URLENCODED>'`
     — Jina renders DuckDuckGo HTML without the bot-block Google/Bing throw.
   - Cited article links: fetch via `https://r.jina.ai/<URL>` to confirm they
     exist and what they ACTUALLY say (don't trust the paste's paraphrase).
3. **Flag every discrepancy explicitly** in a Claim | Verdict | Evidence table
   (real / unverified / false).
4. **Then act** on the verified core: implement, correct, or summarize. The user
   wants the working result, not just a verdict.

## Variant: an AI "code review" / audit of YOUR repo (fabricated defects)
A different but related trap: another AI pastes a numbered "review", "audit", or
"35 things wrong with your code" doc about *this* project. These are frequently
written **without reading or running the code** and contain FALSE defect claims
that, if trusted, waste effort "fixing" working code. Session 2026-07-16 proved
this: a pasted 35-item review claimed `@remotion/bundler` was missing (it was
installed — `require.resolve` succeeded), `agentDecide` "ignored scoreCandidate"
(it called it at line ~170), `scoreCandidate` "was never tested" (it was, in
`enhancement.test.ts`), and the Remotion path "had no fallback" (it did). All
four headline items were false.

Disprove, don't trust — concrete probes (run them, read output, THEN judge):
- **"Module missing / import crashes"** → `node -e "require.resolve('pkg')"` or
  `grep -rn "from 'pkg'" src | head`. Installed? Then the claim is false.
- **"Function X is never called / ignored"** → `grep -rn "nameOfFn" src` and read
  the call site. A call with the return value used = wired, not "ignored".
- **"Never tested"** → `grep -rln "nameOfFn\|describe('X'" src/**/*.test.ts`.
  Existence of a test file + assertion = tested.
- **"Dead code / unused"** → `grep -rn "symbolName" src` across the repo. Zero
  references outside its own definition = truly dead; otherwise it's used.
- **"Crashes / wrong path / hardcoded"** → read the actual lines cited. Often the
  code already mitigates it (e.g. relative-path + escape already present).
Deliver a **Claim | Verdict(real/false) | Evidence** table, keep the genuinely
true items, skip the false ones. Then implement only the verified-real subset.

### Pitfall within this pitfall: brittle tests mask real regressions
A test that asserts a *literal implementation string* (e.g. "keywords must
include `'video of lions'`") forces the code to emit low-quality output just to
stay green. When fixing such a test, assert **quality properties** instead
(distinct, deterministic, no degenerate phrase), not the literal token. This
session removed a `"<kind> of <topic>"` keyword hack that hurt search relevance
and replaced the test with property assertions — output quality improved AND the
test still guarded the behavior.

## Variant: a pasted "improvement plan" for YOUR large codebase
Same trust-but-verify discipline, but the doc is styled as a prioritized
"here's what to fix next" list for *this* repo (e.g. an agentic video pipeline,
a 2000-line render engine). Session 2026-07-18 proved these routinely contain
**false "not done" claims about work completed in earlier sessions**:
- **"Feature X is not wired into render"** → it WAS wired in a prior session.
  Always `grep -rn "symbolName" src` for the consumption site before accepting
  "not wired". The prior session's commit + the live `main` are the source of
  truth, not the paste.
- **Hallucinated file paths / line counts.** The paste listed ~21 "effect
  modules" at a flat path (`src/agentic/`) that didn't exist; they actually live
  under `plugins/{audio,motion,...}/` and `operations/`. Verify existence + size
  with `find src -name "$f.ts"` and `wc -l`, NOT trust the stated path/LOC.
- **Fabricated "untested files" inventory.** A claim like "`orchestrate.ts` has
  NO dedicated test" may be true — but "these 12 files are all untested" is often
  padded with files that don't exist or are already covered indirectly. Check:
  `ls src/agentic/$f.test.ts` and `grep -rln "symbolUnderTest" src/agentic/*.test.ts`.

Concrete verification recipe for a pasted improvement plan (run, then judge):
```bash
# 1) Does the "not wired" feature already exist? grep the consumption site.
grep -rn "resolveCaptionTheme\|captionTheme" src/agentic/orchestrate.ts
# 2) Does the named file exist AT ALL, and what size? (paste paths lie)
for f in genre-style platform-export dispatch beat-sync glitch film-grain; do
  found=$(find src -name "$f.ts" 2>/dev/null | head -1); echo "$f -> ${found:-NOT FOUND}"; done
# 3) Is a supposedly-untested file already covered?
ls src/agentic/gate.test.ts 2>/dev/null || echo "no standalone gate.test.ts"
grep -rln "runFinalGate" src/agentic/*.test.ts
# 4) Is a claimed bug real or stale? read the actual lines.
grep -nE "readFileSync\(.*\)\.toString\('base64'\)" src/agentic/brain.ts
```
Deliver a **Claim | Verdict(real/false/stale) | Evidence** table, keep the
genuinely-true items (the gate had no standalone test; brain.ts DID read images
with no size cap; acquireAssets DID fan out via Promise.all unbounded), and SKIP
the false ones (caption-theme wiring; the 21-module list; the "race condition"
that wasn't a real read-then-populate race). Then implement only the verified-real
subset — and prefer extracting + unit-testing PURE exported helpers from a huge
file over trying to test the whole 2000-line module (see
`software-development/remotion-ffmpeg-video` references for the AVG pattern).

## Pitfalls
- **Star counts in AI comparisons are routinely wrong.** Across pasted
  OpenClaw-vs-Hermes docs, Hermes stars were 30k, 30k, then 66k — all wrong
  (live: 214,750). OpenClaw live: 382,920. NEVER trust an AI doc's metric; re-pull.
- **Version numbers are ALSO hallucinated.** A July-2026 Hermes/Paperclip doc
  claimed 'Hermes v0.18.0 (July 2026)' and 'Paperclip v2026.626.0 (June 2026)' —
  live GitHub showed Hermes **v0.18.2** (tag v2026.7.7.2) and Paperclip
  **v2026.707.0** (July). A claimed version that isn't in `/tags` is fabricated.
- **Release/launch DATES are hallucinated too.** The same doc claimed Hermes
  'released Feb 2026' and '140,000 stars in under 3 months' — live `created_at`
  was **2025-07-22** and stars **214,936**. Always check `created_at` +
  release `published_at`; do not trust an AI-stated launch month.
- **License claims are often wrong.** OpenClaw is `NOASSERTION` (custom), NOT MIT.
  Hermes is MIT. Verify via `license.spdx_id`.
- **'Zero stale issues' / precise percentages are usually invented.** Open-issues
  counts are real (GitHub API); qualitative 'stale %' is not — fabricated precision.
- **Model/spec claims may be partly right.** Verify model names; some are real,
  some invented. Check what you can falsify.
- **Don't reject the whole doc.** Positioning/philosophy text is usually sound;
  only the numbers lie. Keep the useful frame, fix the facts.
- **Don't over-verify opinion.** 'OpenClaw is better for orchestration' needs no
  fetch — only check claims you can falsify.

## Variant: a pasted "official docs" CONFIG block (wrong schema)
Another recurring trap: the user pastes a polished "official documentation" block
— YAML config, API examples, with citation footnotes — that is actually
AI-generated (often ChatGPT). Session 2026-07-20 proved this: a Stripe
MCP config paste carried `utm_source=chatgpt.com` tracking on BOTH its
citation links, a tell it was scraped from a ChatGPT answer, not the live docs.
It led with a STATIC BEARER TOKEN (`headers: Authorization: "Bearer ***"`)
and NESTED the tool filter under `tools: include:` — both WRONG vs the
real Hermes MCP docs (Stripe is OAuth-2.1-only; `include`/`exclude` are
DIRECT keys under the server entry, not nested under `tools:`).

Verify a pasted config/doc block like this:
1. SMELL-CHECK the links. `utm_source=chatgpt.com` on citation URLs =
   ChatGPT-sourced, NOT authoritative. Re-pull the real docs page
   (`browser_navigate` to the canonical URL) and grep the live snapshot for
   the real schema/keywords.
2. RE-PULL the live primary source for any schema claim. For Hermes MCP,
   load `https://hermes-agent.nousresearch.com/docs/user-guide/features/mcp`,
   save the browser snapshot, then verify exact KEY NAMES + NESTING:
   ```bash
   grep -in "auth: oauth\|mcp.stripe.com\|exclude:\|include:\|tools:" <snapshot.txt>
   ```
   Confirm whether filters are server-level keys or nested under `tools:`.
3. CONFIRM the auth method the docs actually name. If the paste says
   "static bearer" but the docs list the provider under "OAuth 2.1 required"
   hosted servers, the paste is wrong — use `auth: oauth`.
4. DELIVER a Claim | Verdict | Evidence table, then ACT on the verified
   core (e.g. write the correct config block). The user wants the working
   result, not just a "you were wrong" verdict.

MCP schema + the agentic-payment provider comparison this session produced.

## OSS ML / TTS license & size verification (voice-cloning & model-stack case)

When the pasted AI doc pitches "open-source, free" **AI models / TTS / voice
cloning** tools (e.g. for a self-hosted pipeline), the license and feasibility
claims need a deeper pass than a single `license.spdx_id` lookup:

1. **`NOASSERTION` usually HIDES a restrictive license — never read it as MIT.**
   GitHub reports `NOASSERTION` when the LICENSE file isn't a standard SPDX id.
   That frequently means a **custom non-commercial / research-only** license.
   Proven this session: Fish Speech shows `NOASSERTION`, but its raw LICENSE is
   the *"Fish Audio Research License"* which states **"Any Commercial use
   requires a separate license"** — unusable for a published/commercial MIT
   project. **When spdx_id is NOASSERTION, fetch the raw LICENSE and read it.**
   ```bash
   timeout 20 curl -s 'https://raw.githubusercontent.com/<owner>/<repo>/main/LICENSE' | head -30
   ```

2. **Copyleft that breaks an MIT shipping path.** Even a "real" open-source
   license can poison a clean MIT product:
   - **AGPL-3.0** (e.g. OmniVoice Studio) — network use forces source disclosure;
     incompatible with a clean MIT SaaS/tool. Reject for the shipping path.
   - **MPL-2.0** (e.g. Coqui XTTS) — file-level copyleft + frequently **archived
     / unmaintained** (~2 yrs dead). Keep legacy wiring only; don't adopt new.
   - **MIT / Apache-2.0** = the only clean choices for an MIT project.

3. **"Open-source" with NO real repo = likely proprietary/marketing.** A pasted
   doc claimed a "Voicebox desktop app" was open-source; its only citations were
   Instagram reels + a docs site, and no real repo existed. The genuinely
   open-source one (`jamiepine/voicebox`, MIT, 42k★) was a *different* repo.
   **Before trusting an "OSS" claim, confirm the actual repo exists, its license,
   and `pushed_at` (maintenance).** A claim with only social-media citations is
   unverified — flag it.

4. **Prove RAM-feasibility via HuggingFace weights size** (critical on low-spec
   laptops). Star/license checks don't tell you if a model *fits*. Sum the
   safetensors/ckpt files:
   ```bash
   timeout 20 curl -s 'https://huggingface.co/api/models/<owner>/<repo>/tree/main?recursive=true' | python -c '
   import sys,json
   d=json.load(sys.stdin); tot=0
   for f in d:
       if isinstance(f,dict) and f.get("path","").endswith((".safetensors",".ckpt",".pt",".bin")):
           sz=f.get("size")
           if isinstance(sz,int): tot+=sz
           print(" ",f["path"], (sz//1024//1024 if isinstance(sz,int) else sz),"MB")
   print("TOTAL", tot//1024//1024,"MB")'
   ```
   Real example from this session: Kokoro 312 MB (fits 6 GB box) vs VibeVoice-ASR
   15.9 GB (impossible). Also check **HF-gated** models (`401` on the API → needs
   login) — Chatterbox is gated, which adds friction vs F5-TTS (open).

5. **Cloning vs not — read the model's actual capability, not the doc's label.**
   RVC is "open-source voice" but does *voice conversion* (re-voice existing
   audio), NOT text-to-speech. VibeVoice-TTS had its code *removed* by Microsoft.
   Kokoro ships fixed voices (no cloning). Verify the capability matches the
   requirement before recommending.
